# 倍半速变化方案评估分析（94 BPM ↔ 188/187 BPM 场景）

> **声明**：**本文件仅作可行性与方案分析，按最高优先级限制未对当前运行时音频识别代码做任何修改。**
> 本文引用的全部类、方法、常量与逻辑分支均核对自当前工程冻结音频核心 [`src/audio/frozen-audio-core.js`](../src/audio/frozen-audio-core.js)（字节校验零修改）。

## 一、问题背景与原版节拍检测器 `x1` 现状剖析

在实际听歌跟拍场景中，用户常会遇到同一首曲子在稳态播放时，界面展示的 BPM 与人物点头频率突然发生近似 **2 倍或 0.5 倍** 跳变的现象（典型案例：稳定锁定在 **94 BPM** 附近后，遇到副歌密集踩镲、双拍军鼓或十六分音符律动时突然跳到 **187~188 BPM**，随后又可能跳回 94 BPM）。

要科学评估“当程序试图从 94 BPM 改成 ~188/187 BPM（或对应半速）时，是否可以忽略变化、保持原点头节奏”，首先必须看清原版节拍检测器 `x1`（及动画函数 `m1`）是如何处理倍频程跳变的。

### 1.1 搜索空间与 94 ↔ 188 BPM 的天然重叠

- 搜索周期边界常量：`Lt = 10`（10 ms/bin），搜索 lag 范围为 `Rl = 30` 到 `sl = 100` bins，即 **300 ms ~ 1000 ms（对应 60 BPM ~ 200 BPM）**。
- `94 BPM` 对应周期约为 `60000 / 94 ≈ 638.3 ms`（`lag ≈ 63.8` bins）；其倍速 `188 BPM` 对应周期约为 `319.1 ms`（`lag ≈ 31.9` bins）。两者**同时落入 `[30, 100]` 合法搜索区间内**（同理如 `80 ↔ 160`、`75 ↔ 150`、`90 ↔ 180` 均落在该区间）。
- 虽然 `estimate()` 中通过中心为 110 BPM 的高斯先验 `p1(L)` 与 `6000 / X > 145` 折半启发式（`!R && H[T] >= H[X]*0.5 && et[T] > et[X]*0.95 && !this.bassCadenceSupports(..., X*Lt, 3, true)`）抑制了一部分高 BPM 误判，但一旦乐段中打击乐特征使 `R`（`percussive`）置 `true`、或副歌高频节奏密集拉高半周期自相关得分，候选 `rawF * Lt` 依然会切换到 `~319 ms`。

### 1.2 原版代码中的三条倍半速控制路径

1. **4 秒窗口切歌快速重锁通道（`process(h)`）**：
   - 当锁定超过 6 秒（`h - this.committedAt > 6000`），每 `400 ms` 用 `estimate(400)` 探测最近 4 秒是否发生切歌。
   - 关键排除条件为：`!(Math.abs(Math.abs(Math.log2(w / this.lockedLagMs)) - 1) < 0.08)`。
   - **结论**：`freshCount >= 4` 快速切歌通道**已经主动排除了** `2x / 0.5x` 倍频关系（约 `1.89x ~ 2.11x` 或 `0.47x ~ 0.53x`）。因此，**94 ↔ 188 BPM 跳变并不是从切歌快速重锁通道进入的，而是全部落入主锁定更新函数 `updateLock(h, this.estimate())`**。

2. **主锁定更新通道（`updateLock(h, m)`）——不对称的倍半速门控**：
   - **对“2x 周期（BPM 减半）”有拦截**：当 `x / this.lockedLagMs > 1.85 && x / this.lockedLagMs < 2.15` 且 `this.bassCadenceSupports(h, this.lockedLagMs)`（原周期仍获至少 2 次强低音间隔支持）时，直接 `return` 拦截。
   - **对“0.5x 周期（BPM 翻倍，如 94 → 188）”拦截较弱**：若半周期满足 `H = x / lockedLagMs ∈ (0.46, 0.54)`，只要同时触发 `nt = H && bassCadenceSupports(h, x, 3, false, 0.55)`（中等强度 `> 0.55` 的低音间隔满足 3 次），或者在原周期保留判断 `U >= et * M`（`et = 0.65`）失败后，进入最终倍频程切换判据 `rt`：
     - `rt` 定义：`Math.abs(Math.log2(x / lockedLagMs) - Math.round(Math.log2(x / lockedLagMs))) < 0.06 && Math.abs(Math.round(Math.log2(x / lockedLagMs))) >= 1`。
     - **20 秒初始纠偏窗口（`acquiredAt` & `initialOctaveCorrected`）**：在 `h - this.acquiredAt < 20000 && !this.initialOctaveCorrected` 内，只要满足 `st`（或 `h - this.acquiredAt < 6500` 的 `dt` 窗口），门限比 `Mt` 极低（`0.45 ~ 1.15`），连击仅需 `k = 2` 或 `5` 帧（`0.4s ~ 1.0s`）即可完成倍半速纠正，并在 `commitWith` 中将 `initialOctaveCorrected` 置为 `true`。
     - **稳态后仍允许倍频程跳变**：即使已过 20 秒且 `initialOctaveCorrected === true`，只要新峰对旧峰比值 `X = M / U >= 1.8` 且 `m.conf >= 1.25` 连续出现 `k = 10` 帧（约 `2.0s`），`updateLock` **依然会执行 `commitWith` 从 94 BPM 切到 188 BPM**（一旦主歌进副歌伴随半周期能量显著抬升，10 帧很容易达成）。

3. **UI 显示平滑层（`displayBpm(h)`）与物理跟拍层（`m1`）**：
   - `displayBpm(h)` 平时采用每 `>= 100 ms` 采样一次、保留 **9 样本中位数**（`shownSamples`）+ **1 BPM 死区** + **400 ms 滞回**（`h - shownCandAt > 400`）来避免数字跳闪。
   - 然而 `commitWith` 在 `|f / lockedLagMs - 1| > 0.12` 时会**直接清空 `shownSamples = []` 并重置 `shownMedian = 0, shownCand = 0`**；同时 `this.lockedLagMs` 与 `this.nextBeat` 在调用 `commitWith` 的同一毫秒就已经变成 ~319 ms，直接驱动人物 `m1(now, nextBeatAt, periodMs, hitStrength)` 瞬间加速一倍点头。

## 二、可行性与视觉观感依据

在满足特定约束的前提下，**对“稳定锁定后的倍半速跳变”进行抑制或高阈值滞回过滤，在技术上可行，在视觉观感上通常显著优于当前行为**：

1. **音乐拍号等价性**：在绝大多数现代流行、电子、ACG 与摇滚音乐中，94 BPM 与 188 BPM 往往对应同一首歌的“四分音符拍”与“八分音符细分拍”（或 Half-time / Double-time 律动）。人物在 94 BPM（每拍约 638 ms）点头时，幅度舒展、观感优雅自然；而突然切到 188 BPM（每拍约 319 ms）后，`m1` 余弦窗脉冲宽度从 `170 ms` 挤压至 `min(170, 319 * 0.3) ≈ 95.7 ms`，人物会骤然变成高频快速抖头，破坏陪伴氛围。
2. **局部节奏密度变化不应等价于速度翻倍**：副歌段常见的 Hi-hat 加密、双拍军鼓填充或贝斯八分切分，会让频谱通量（`spectralOdf`）与整体 ODF 在 `lag/2` 处的自相关得分临时超越原 `lag`（触发 `X >= 1.8`），但歌曲真正的骨架拍速（Macro Beat）并未改变。
3. **现有架构已隐含“倍频不应按普通切歌处理”的设计倾向**：原版代码在 `process()` 的 `freshCount` 切歌重锁通道中已经显式排除了 `|log2(w / lockedLagMs)| ≈ 1` 的倍频跳变，这说明原作者也意识到 2x/0.5x 跳变往往属于拍层歧义而非真正换歌。

## 三、适用前提条件（缺一不可）

任何“忽略或高滞回抑制 2x / 0.5x 跳变”的策略，**绝对不能无条件套用于全局**，必须同时满足以下 **4 项前置前提**：

1. **必须处于稳定锁定态（`locked === true`）**：
   - 未锁定时的初次捕拍（`!this.locked`）及刚锁定的初始纠偏观察期内（如 `acquiredAt` 后前 `10s ~ 20s` 且尚未完成 `!initialOctaveCorrected`），**必须保留正常倍频程纠偏能力**，确保前奏入拍错锁时还能自行修正。
2. **非静音恢复或时间断层重启**：
   - 若刚经历 `silentSince > 900 ms` 静音清零重置、或 `lastFrameAt` 间隔 `> 200 ms` 导致的线程卡顿重置（状态均已回到 `locked = false`），随后的首轮锁定属于全新识别，不应受历史速度约束。
3. **无切歌 / 乐段彻底突变信号**：
   - 若前后音频在全局能量均值、频谱质心分布上发生剧烈跳变（或歌曲切换间隙存在 `300~900 ms` 短暂低电平过渡），应视为可能换歌，不得沿用上一首歌的倍速锁定记忆。
4. **原锁定周期在当前窗口仍获得足够的能量与相位残差支持**：
   - 查看原周期邻域得分 `U = max(scores[R-1..R+1])` 与新峰值 `M = scores[rawLag]`：只有当原周期仍保留明显能量与周期性（例如 `U / M` 不低于保底门槛如 `0.30 ~ 0.35`，且原周期 `coverageByLag[R]` 或 `bassCadenceSupports(h, lockedLagMs)` 仍成立）时，才说明“94 BPM 骨架依然存在，只是 188 BPM 细分拍变强了”；反之若原周期能量完全坍塌，则说明曲目可能已真实切换。

## 四、具体分层实施方案（可配置滞回，拒绝“一刀切硬禁”）

如果在后续非冻结期需要迭代改进该行为，建议采用**三层解耦 + 可配置滞回**的渐进式工程方案，而非在 `updateLock` 中简单写死 `if (rt) return;`：

### 4.1 第 1 层：内部候选估计层（保持透明观测）
- 保持 `estimate()` 的自相关计算、频谱周期性 `periodicity` 与 `coverageByLag` 真实出力不变。
- 扩展输出诊断上下文（不改变算法评分本身）：明确计算候选相对当前锁的倍频关系 `octaveRatio = x / lockedLagMs`、原周期保留率 `supportRatio = U / M`、以及原周期低频支撑度 `origBassSupported = bassCadenceSupports(h, lockedLagMs)`。

### 4.2 第 2 层：稳态锁定与可配置滞回门控层（`periodMs` 跟拍网格层）
引入可配置策略参数 `octaveLockMode`（例如 `'legacy'` / `'hysteresis'` / `'lock_after_settle'`，默认推荐稳健滞回 `'hysteresis'`）：

- **阶段 A — 初始建锁与纠偏期（`!initialOctaveCorrected && h - acquiredAt < 20000`）**：
  - 基本沿用原版 `dt` / `st` 窗口逻辑，但要求**双向校验**：若从慢拍（94）跳到快拍（188），除了 `nt` 低频支撑外，建议额外检查候选 `188 BPM` 是否超出温和上限（或要求 `bassCadenceSupports` 使用更严格的强低音阈值 `> 0.72`），避免歌曲前奏双倍踩镲一响就立即错锁成 188 BPM。
- **阶段 B — 稳态防抖期（`h - acquiredAt >= 20000` 或 `initialOctaveCorrected === true`）**：
  - 当检测到候选落入倍/半速容差带（`| |log2(x / lockedLagMs)| - 1 | < 0.08`）时：
    1. **检查原周期是否仍存活**：若 `U / M >= 0.35` 或 `origBassSupported === true`，认定原周期仍在歌曲中成立；
    2. **启动“稳态倍频滞回计数器”而非 2 秒即切**：将稳态倍频切换门限从 `X >= 1.8, k = 10 (2s)` 提高至双条件滞回（例如 `X >= 2.8` 且 `U / M < 0.28`，同时连续确认时长延长至 `6s ~ 8s`，即 `k >= 30~40` 帧）；
    3. **对称化拦截**：对 `0.5x`（BPM 翻倍，如 94 → 188）与 `2x`（BPM 减半，如 188 → 94）采用一致的稳态保护规则——原周期只要仍获有效律动支持，即保持原 `lockedLagMs` 与 `nextBeat` 网格，**忽略**短暂的倍/半速波动；仅允许微小的相位纠偏（±8 ms）和 ±3.5% 以内的微调。
    4. 若用户主动开启“**锁定当前拍速倍率**”开关（类似 DJ 软件的 `Lock Octave`），则仅在静音重置或手动点击切换音源后才释放倍频锁。

### 4.3 第 3 层：BPM 界面显示平滑层（`displayBpm` 层）
- **保持显示与物理跟拍同源**：`displayBpm` 必须继续读取最终裁决后的 `lockedLagMs`，严禁“底层用 188 BPM 驱动点头，界面却假装显示 94 BPM”（原因见第五节风险 4）。
- **取消粗糙清零**：若某次合法纠偏确实触发 `commitWith` 且属于微幅调整，保留合理的平滑缓冲；若发生跨倍频程的合法切换（如真的切歌了），再立刻刷新 `shownSamples` 与界面显示。

## 五、必须警惕的 4 大风险与边界场景

在评估是否上线倍半速忽略策略时，必须充分预判以下四个典型失效场景及应对手段：

### 风险 1：初次锁错倍/半速后，后续永远无法纠偏
- **场景描述**：很多歌曲前奏（Intro）只有八分音符分解吉他、钢琴琶音或双倍速电子 Hi-hat，前 4 秒软件非常容易错锁在 **188 BPM**（实际曲速 94）或错锁在 **70 BPM**（实际曲速 140）。
- **后果**：如果方案设计成“一旦锁定就禁止任何 2x / 0.5x 变动”，那么第 10 秒真正底鼓/主歌进来时，人物将**整首歌永远以错误倍率抽搐或迟钝点头**，直到歌曲放完。
- **缓解措施**：必须严格保留 `acquiredAt` 前 20 秒的 `initialOctaveCorrected` 纠偏窗口，且仅在连续稳态确认后才收紧倍频程切换门槛；同时可考虑在 UI 提供一个轻量的“`×2` / `÷2` 手动拍速校正”微调按钮作为兜底。

### 风险 2：真实切歌或编曲突变，新歌恰好落在 `2x / 0.5x` 关系
- **场景描述**：播放器连播或直播背景音从一首 94 BPM 的抒情歌无缝切入一首 188 BPM 的快节奏摇滚/DnB；或者一首 Dubstep / Trap 曲目在 Drop 段真实进入了明确的 Half-time（70 BPM ↔ 140 BPM）。
- **后果**：如果只盯着 `|log2(w / lockedLagMs)| ≈ 1` 就直接拦截，系统会误以为“还在同一首歌的倍频抖动里”，导致换歌后人物依然慢半拍，甚至因为 `process()` 的 `freshCount` 通道同样屏蔽倍频而**完全无法重锁新歌**。
- **缓解措施**：倍频程忽略逻辑必须以**“原周期仍获得足够能量与周期支持（`U / M >= 阈值`）”**以及**“无静音过渡/频谱突跳”**为前提；当原周期分值 `U` 跌破新峰 `M` 的 25%~30% 并持续数秒时，必须放行切换。

### 风险 3：高 BPM 降为半速跟拍时，相位错锚在 `2 / 4` 拍（反拍）导致全曲反拍点头
- **场景描述**：当检测器原本在 188 BPM（每个四分/八分格都点），若通过“保持半速 94 BPM”忽略掉翻倍变化，或把 188 强行折叠回 94 时，原 188 网格上的偶数格（1, 3 拍）与奇数格（2, 4 拍）在数学周期上完全等价。
- **后果**：在流行/摇滚/Hip-Hop 中，第 2、4 拍的反拍军鼓（Snare / Clap）瞬态高频 Flux 往往比第 1 拍底鼓（Kick）更尖锐。一旦 `nextBeat` 相位错锚在 2/4 拍上，桌宠就会出现**“强拍（底鼓）抬头、弱拍（军鼓）低头”的全身反拍违和感**，而且全曲不会自动翻正。
- **缓解措施**：在保持或折半为慢速周期时，相位对齐 `pickPhase` 必须强制优先查询低频底鼓锚点 `bassAnchor(h, lockedLagMs)`（针对 40~250 Hz 强低音加权），确保 `nextBeat` 优先锁定在底鼓强拍上。

### 风险 4：“只锁界面显示 BPM” 与 “锁定实际跟拍点头速度 `periodMs`” 的割裂风险
- **场景描述**：工程实践中容易出现一种“偷懒修法”——为了不让用户看到界面 BPM 数字从 94 跳成 188，只在 `displayBpm()` 或 React 状态层对 `bpm` 做倍频程钳位显示，而没有同步约束 `updateLock` 中的 `lockedLagMs` 与 `nextBeat`（`periodMs`）。
- **后果**：用户眼睛看到界面明明稳稳写着 `94 BPM`，但屏幕上桌宠却以每分钟 188 次的速度疯狂甩头！这种**“视觉动作与数字显示完全脱节”**的 Bug 比单纯显示 188 BPM 更让人困惑。
- **缓解措施**：任何倍半速滞回决策都必须作用于单一事实来源 **`lockedLagMs`（同时决定 `periodMs`、`nextBeat` 与 `displayBpm`）**，确保“界面显示几拍，人物就严格按几拍点头”。

## 六、评估结论与建议

1. **当前版本处理结论**：依据最高优先级冻结原则，当前版本**完全保留原版音频与节拍核心 `x1` / `m1`**，未引入任何实验性倍半速改写，确保现有音频识别稳定性与历史兼容性 100% 受控。
2. **后续迭代推荐路径**：
   - 在业务层具备**高稳定性需求**（如长时间陪伴、自习听歌防突然抽搐）的未来版本中，**推荐落地第四节所述的“稳态可配置倍半速滞回方案”**（区分初始 20s 纠偏期与稳态防抖期，并以“原周期能量保留率 `U/M` + 低频支撑 `bassCadenceSupports` + 相位强拍锚定”作为前置条件）。
   - 同时保留“手动快速纠偏入口”（或未来在解锁草图扩展位后开放手动 `BPM` 锁定），从算法滞回与用户可控性两端彻底解决 94 ↔ 188 BPM 倍半速观感问题。
